Assignment Objectives & Parallel Paradigm

🎯 Assignment Objectives
  • Two GPU-Based Competitors: Autonomous AI agents making decisions via CUDA kernels.
  • Zero CPU Cheating: Entire candidate move evaluation executed on GPU silicon.
  • Hardware Versatility: Native dual physical GPU mode with single-GPU fallback.
  • Real Micro-benchmarking: Sub-millisecond timing using native CUDA hardware events.
  • Tournament Fairness: 10 consecutive matches with alternating starting moves.
⚡ Why Parallelize Tic-Tac-Toe?
  • Sequential CPU Model: Evaluates moves via a serial loop $O(N)$ where $N=9$.
  • CUDA SIMT Architecture: Maps 9 candidate moves directly to 9 parallel GPU threads ($O(1)$ evaluation).
  • Microcosm of Massive Games: Serves as the transparent architectural foundation for scaling to Connect-4, Gomoku, and deep tree searches.

Player O: Strategic CUDA AI

🛡️ Strategic Counter-Play Philosophy

__device__ int count_winning_threats(
    const int* b, int pos, int sym
) {
    int threats = 0;
    for (int i = 0; i < 8; ++i) {
        // If line contains pos + 1 friendly piece
        // and 1 empty cell -> forms an unblocked threat
        if (line_has_two(b, pos, sym, i)) threats++;
    }
    return threats;
}

🔒 Occupied Cell Guard & Early Exit
  • Immediate Filtering: Threads mapped to occupied cells set score to -100000.0f and terminate early.
  • Concurrent Evaluation: Empty cells evaluate heuristics in parallel with zero mutual dependency.
  • Host Argmax Reduction: Host receives the evaluated 9-float score array and picks the maximum valid cell in $O(1)$ time.
MEMORY MANAGEMENT

Constant Memory Caching & Lifecycle

⚡ Broadcast via Constant Memory

The 8 winning geometric lines (3 rows, 3 cols, 2 diagonals) are stored in __constant__ memory: 

__constant__ int d_win_lines[8][3] = {
    {0,1,2}, {3,4,5}, {6,7,8}, // Rows
    {0,3,6}, {1,4,7}, {2,5,8}, // Cols
    {0,4,8}, {2,4,6}             // Diags
};

✓ Cached on-chip in the SM: all 9 threads read winning lines in a single broadcast clock cycle!

🔄 Host-Device Lifecycle
  • Allocation: cudaMalloc for 9 ints (board) and 9 floats (scores).
  • H2D Transfer: cudaMemcpy(..., cudaMemcpyHostToDevice) transfers 36 bytes.
  • Device Execution: Kernel executes in parallel across 9 threads.
  • D2H Transfer: cudaMemcpy(..., cudaMemcpyDeviceToHost) retrieves 36 bytes.
  • Cleanup: cudaFree and cudaEventDestroy guarantee zero memory leaks.
CONCURRENCY & SYNCHRONIZATION

Multi-GPU (Mode A) vs Single-GPU (Mode B)

🚀 MODE A: Dual Physical GPUs

Triggered automatically when cudaGetDeviceCount(≥ 2):

  • Player X: Bound to physical GPU 0 via cudaSetDevice(0).
  • Player O: Bound to physical GPU 1 via cudaSetDevice(1).
  • True hardware silicon parallelism across separate physical graphics cards.
🛡️ MODE B: Single Physical GPU Fallback

Triggered in standard Coursera cloud or single-GPU workstations:

  • Both competitors target cudaSetDevice(0).
  • Two independent CPU threads coordinate turn-taking.
  • Thread Synchronization: std::mutex and std::condition_variable protect shared board state.
  • GPU memory isolation: each AI instance retains private device buffers.
PERFORMANCE PROFILING

Sub-Millisecond Profiling via CUDA Events

⚠️ Pitfalls of Standard CPU Timers
  • CUDA kernel launches are asynchronous.
  • CPU timers like clock() or std::chrono only measure the nanoseconds taken to queue the kernel into the driver ring buffer.
  • CPU timers fail to measure true GPU silicon execution duration.
⏱️ Accurate Hardware Event Profiling
cudaEvent_t start, stop;
cudaEventCreate(&start);
cudaEventCreate(&stop);

cudaEventRecord(start, 0);
kernel_evaluate<<<1, 9>>>(...);
cudaEventRecord(stop, 0);

cudaEventSynchronize(stop); // Wait for GPU
cudaEventElapsedTime(&time_ms, start, stop);

✓ Measures exact physical SM clock cycles converted to milliseconds!
